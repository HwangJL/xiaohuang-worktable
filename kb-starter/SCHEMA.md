# 知识库操作手册（SCHEMA）

本文件是本工作区知识库的唯一规则来源（L0 层，每次会话按需加载）。结构照搬卡帕西 LLM Wiki 方法论：三层 `raw → wiki → schema`，三个操作 `ingest / query / lint`。

核心一句：**原始资料只读存档，知识由 agent 编译成结构化 Markdown wiki；用户只读、只决策，wiki 由 agent 维护。** 不是 RAG（每次检索原始文档），而是提前编译、随后增量更新——新资料进来时，不只写一篇摘要，还要回头更新所有受影响的实体页、概念页和决策页。

---

## 1. 目录结构

```
kb/
├─ SCHEMA.md             规则（本文件，agent 与用户的共同契约）
├─ raw/                  原始资料，用户投放，agent 只读
│  └─ assets/            剪藏图片、截图、PDF 附图
├─ wiki/                 知识库正文，agent 拥有，用户阅读
│  ├─ index.md           内容索引（每个页面一行）
│  ├─ log.md             操作日志（只追加，可 grep）
│  ├─ entities/          实体页  E-xxxx  人 / 系统 / 产品 / 环境 / 模块
│  ├─ concepts/          概念页  C-xxxx  方法、规则、机制、术语
│  ├─ decisions/         决策页  D-xxxx  已确认的决策与其依据
│  ├─ summaries/         摘要页  S-xxxx  一份原始资料的编译结果
│  ├─ comparisons/       对比页  X-xxxx  方案对比、选型分析
│  ├─ issues/            故障页  I-xxxx  环境问题、踩坑记录与规避方式
│  └─ questions/         待确认  Q-xxxx  悬而未决、等用户决策的问题
└─ templates/            六类页面模板
```

`raw/` 与 `wiki/` 的边界不能模糊：raw 里放的是别人写的东西（原样或摘录，带来源），wiki 里放的是我们自己编译出的结论（带状态、带链接、可被后续工作直接引用）。

---

## 2. 分层职责

| 层 | 谁写 | 可变性 | 内容 |
|---|---|---|---|
| `raw/` | 用户 / agent 剪藏 | 只读（agent 不改） | 网页摘录、PDF、会议纪要、外部文档、图片 |
| `wiki/` | agent | 持续增量更新 | 摘要、实体、概念、决策、对比、故障、待确认 |
| `SCHEMA.md` | agent + 用户共同迭代 | 低频，需说明理由 | 结构、命名、流程、加载预算、写作纪律 |

用户对 wiki 有读权、有否决权，没有编辑义务；agent 对 wiki 有写权，但没有擅自改变"已确认决策"的权力（见 §8）。

---

## 3. 分级加载（token 预算）

按需逐级加载，**不读完上一级不读下一级**：

| 级别 | 内容 | 预算 | 何时读 |
|---|---|---|---|
| L0 | `kb/SCHEMA.md` 的 §1 §4 §8 | ~200 字 | 第一次在本工作区做知识相关的任务 |
| L1 | `wiki/index.md` | 1–2K | 每次涉及已有项目知识的任务开始前 |
| L2 | `grep` 命中的页面摘要段 | 2–5K | 索引指向了相关页面之后 |
| L3 | 完整页面 | 5–20K | 确实要基于该页做设计或改文档时 |

禁止一上来把 `wiki/` 全目录读进上下文；禁止跳过 L1 直接随机搜页面。

## 4. 三个操作

### 4.1 Ingest（摄入一份新资料）

1. 资料落到 `raw/`，文件名 `YYYY-MM-DD-<slug>.md`，头部写明来源 URL、抓取日期、是否全文/摘录、可信度。
2. 通读，判断它触及哪些既有页面：`grep` 关键词扫 `wiki/`，再看 `index.md` 的标签列。
3. 写摘要页 `S-xxxx`：核心结论、关键事实、可直接引用的数字/规则、与已有知识的差异。
4. **增量更新关联页**：更新受影响的实体/概念/决策页；发现新旧矛盾时，不要静默改写，在页面「冲突/存疑」段落记录两版说法及各自来源。
5. 新出现的独立概念或实体，开新页并在既有页面加反向链接。
6. 更新 `index.md`（新增行 + 一句话摘要 + 标签 + 状态）。
7. 追加 `log.md`：`## [YYYY-MM-DD HH:mm] ingest | <资料标题>`，写清读了什么、改了哪些页。

一份资料触发 3–15 个页面改动是正常量；只写一篇摘要、不动关联页，视为摄入未完成。

### 4.2 Query（基于知识库作答）

1. 读 `index.md`，按标题/标签定位 1–3 个候选页。
2. 读候选页正文；不足再 `grep` 全库补充。
3. 作答时标明依据页（`E-0001` / `D-0002` 等），不把 wiki 里标 `待确认` 的内容当事实。
4. 回答若产生新结论（对比、新方案、根因分析），**回写成新页或更新既有页**——这是"每次提问都让知识库变厚"的机制，不做回写的分析等于没发生。
5. 追加 `log.md`：`## [YYYY-MM-DD HH:mm] query | <问题>`，记录建/改的页面。

### 4.3 Lint（健康检查）

定期（或用户说"体检一下知识库"时）跑一遍：

| 检查项 | 做法 | 处理 |
|---|---|---|
| 矛盾 | 同一定义/数值在不同页出现不同版本 | 记入该页「冲突/存疑」，标 `待确认` |
| 过时 | 页面结论已被新决策取代 | 状态改 `历史`，正文顶部写明被谁取代 |
| 孤立页 | 除 `index.md` 外无任何入链 | 补链接，或合并进相关页后删除 |
| 幽灵概念 | 正文提到但无独立页的实体/概念 | 建页，或明确标注"不单独立页及原因" |
| 索引漂移 | `index.md` 与目录实际文件不一致 | 全量比对并修正 |
| 缺口 | 结论缺来源、缺数字、缺边界 | 记入 `questions/`，必要时联网补齐 |
| 模板漂移 | frontmatter 字段缺失或类型不符 | 补字段 |

结果追加 `log.md`：`## [YYYY-MM-DD HH:mm] lint | 第 N 次`，并在报告里列出"建议接下来研究什么"。

## 5. 命名与 ID

- 文件名：`<ID>-<slug>.md`，slug 用英文小写连字符；ID 前缀按类型固定：`E` 实体、`C` 概念、`D` 决策、`S` 摘要、`X` 对比、`I` 故障、`Q` 待确认。
- ID 单调递增，不复用、不改号。删除页面时保留 ID 空号。
- 标题用中文人话，不用 slug 当标题。

## 6. Frontmatter（所有页面必填前 8 项）

```yaml
---
title: 一句话标题（中文）
id: E-0001
type: entity            # entity | concept | decision | summary | comparison | issue | question
project: xiaohuang-mode # dsh-profile | xiaohuang-mode | kb | 具体业务项目名
status: 正式            # 正式 | 待确认 | 历史
confirmed: 2026-11-21   # 用户确认日期；待确认为 null
scope: 一句话说明这条知识在什么范围内有效
sources:                # 来源；没有来源的推断写成 "(推断)"
  - https://example.com/x
tags: [dsh, preset]
created: 2026-11-21
updated: 2026-11-21
---

## 摘要
（1–3 行，一句话说清这页主张什么）

## 正文
...

## 关联
- [[E-0002]] 关系说明

## 冲突/存疑        ← 无内容时写"无"
## 变更记录
- 2026-11-21 建页（来源：S-0001）
```

`status` 三档对应人设第十一节的正式/待确认/历史知识：`正式` 才能作为后续设计依据，`待确认` 只能作为参考并显式标注，`历史` 只用于追溯。**未经确认的内容不得覆盖 `正式` 页的结论。**

## 7. 页面模板

| 类型 | 模板 | 必填段落 |
|---|---|---|
| 实体 | `templates/entity.md` | 是什么 / 关键属性 / 与谁交互 / 边界 |
| 概念 | `templates/concept.md` | 定义 / 适用条件 / 反例 / 常见误用 |
| 决策 | `templates/decision.md` | 背景 / 决策 / 依据 / 影响 / 替代方案 / 谁确认 |
| 摘要 | `templates/summary.md` | 资料信息 / 核心结论 / 可引用事实 / 与既有知识差异 |
| 对比 | `templates/comparison.md` | 对比对象 / 维度表 / 推荐与理由 / 适用边界 |
| 故障 | `templates/issue.md` | 现象 / 复现条件 / 根因 / 规避 / 未解部分 |
| 待确认 | `templates/question.md` | 问题 / 影响 / 选项 / 我的建议 / 等谁确认 |

## 8. 写作纪律

1. **每个结论带来源**：外部说法写 URL 或 `raw/` 文件；本项目事实写配置行号或命令输出。没有来源的写成"(推断)"。用户会抽查，不准编。
2. **一页一个主张**：页面按单一实体/概念/决策拆开，不写大杂烩长文；长文靠链接拼接。
3. **中文正文，英文 slug**；术语首次出现给中英对照。
4. **不复制粘贴原文**：摘要用自己的话压缩，原文留在 `raw/` 里。
5. **矛盾不静默消失**：两版说法并存并标冲突，由用户裁决。
6. **已确认决策不可擅改**：为了让文档自洽而改用户确认过的决策，是禁止操作；只能标"需重新确认"（与人设第十节 5 一致）。
7. **日期用本地时区（Asia/Shanghai）**，格式 `YYYY-MM-DD`。

---

## 9. 不写入知识库的内容

- 未确认的推测、临时讨论、草稿方案（暂放 `questions/` 或留在会话里）；
- 一次性任务过程、命令历史、纯聊天记录；
- 已被新决策取代的旧结论（标 `历史` 保留，不删除，也不当依据）；
- 未经用户同意就对外部资料做的"我们应当如何做"的断言。
